# war3parser 生态总体设计

三块业务:**联机平台**(可自部署 + 权威服务器)、**地图站**(上传/下载)、**共用客户端**。
本文只讲**三者如何咬合**;地图仓库本身的设计见 [DISTRIBUTION_DESIGN.md](./DISTRIBUTION_DESIGN.md)。

---

## 1. 枢纽:地图身份

这三块能不能真正连通,不取决于产品设计,取决于一件很具体的事——**能否让"地图站里的一条记录"和"房间里 host 广播的那张图"是同一个东西**。

WC3 联机时,host 通过 W3GS 协议广播四个字段,客户端拿本地文件算一遍来比对:

| 字段 | 含义 | 现状 |
|---|---|---|
| `map_size` | 文件字节数 | 已有 |
| `map_info` | 整个 `.w3x` 文件的 CRC32 | ❌ 未实现 |
| `map_crc` | 对特定文件序列的滚动哈希(4 字节) | ❌ 未实现 |
| `map_sha1` | 同序列的 SHA1(20 字节,1.23+) | ❌ 未实现 |

后两个的计算方式(GHost++ / Aura 的 `CMap::Load` 逻辑)是按**固定顺序**喂入:

```
common.j → blizzard.j → 魔数 0x03F1379E →
war3map.j (或 scripts\war3map.j) → war3map.w3e → war3map.wpm →
war3map.doo → war3map.w3u → war3map.w3b → war3map.w3d →
war3map.w3a → war3map.w3q
```

> ⚠️ 这个序列需要对着 Aura / GHost++ 源码逐字节核对一遍再落地。文件列表和魔数我有把握,但缺失文件的跳过规则、`common.j` 的版本差异需要实测验证。

**两个必须正视的复杂性:**

1. **`common.j` / `blizzard.j` 不在地图里**,它们来自游戏安装目录(`War3Patch.mpq`)。这意味着 `map_crc` / `map_sha1` **随游戏版本变化**——同一张图在 1.26 和 1.27 下算出的值不同。所以 manifest 里不能只存一个值,要存一张**按游戏版本索引的表**:

```rust
pub struct W3gsIdentity {
    pub map_size: u32,
    pub map_info: u32,                        // CRC32,与游戏版本无关
    /// 按游戏版本分别计算。key 例:"1.26a" / "1.27b" / "1.31.1"
    pub per_version: BTreeMap<String, W3gsChecksum>,
}
pub struct W3gsChecksum { pub crc: u32, pub sha1: [u8; 20] }
```

2. **计算需要 common.j 副本**。做法:服务端(Action)持有各主流版本的 `common.j`/`blizzard.j` 及其 sha256,发布时一次性把所有版本的校验值都算出来写进 manifest。**客户端永远不需要自己算**——直接从 registry 拿。这把复杂度集中到了一处。

### 1.1 反查是三块连通的实际接口

```
GET /v1/lookup?sha1=<map_sha1>&size=<n>&version=1.26a
  → { slug, version, digest, name, minimap }
```

有了它,客户端进房间的流程变成:

```
收到 host 广播 {size, crc, sha1}
  → 本地已装图里比对 → 命中?直接就绪
  → 未命中 → GET /v1/lookup → 从国内 CDN 拉(几秒)→ 就绪
```

对比现状(从 host 走游戏内 P2P 慢速传图,10 MB 要几分钟且经常失败),**这是普通玩家能立刻感知到的价值,也是整个生态最有说服力的单点功能**。

## 2. 客户端形态

一个本地 daemon + 一个 UI,三件事:

```
┌──────────────────────────────────────────────┐
│  w3hub (Rust, 本地进程)                       │
├──────────────┬───────────────┬───────────────┤
│ 地图管理      │ LAN 伪造       │ W3GS 隧道      │
│ install/sync │ UDP 6112 广播  │ TCP 转发       │
│ (§见分发文档) │ 把远程房间伪装  │ 到 lobby 服务器 │
│              │ 成局域网房间    │ 或 P2P 直连    │
└──────────────┴───────────────┴───────────────┘
                      ▲
                      │ 不注入、不改游戏文件
                 ┌────┴─────┐
                 │  War3.exe │
                 └───────────┘
```

**LAN 伪造**是第三方平台(11 平台、GHost++、Aura、W3Champions)的通用做法:在本机伪造局域网广播,让 WC3 以为在打 LAN。**不需要注入游戏进程、不需要改动游戏文件、兼容所有版本**——这一条决定了整个方案的可行性和维护成本。

共用客户端的真实含义不是"两个功能塞进一个 exe",而是:**地图状态是联机流程的一部分**。装图、校验、进房间在同一个进程内闭环,没有"先去网站下图再回来开游戏"这个断点。

## 3. 联机:权威服务器 + 自部署

### 3.1 职责切分

| | 权威服务器(你运营) | 自部署服务器(社区) |
|---|---|---|
| 身份/账号 | ✅ 唯一来源 | ❌ 向权威验证(或离线模式) |
| 地图 registry 索引 | ✅ | ❌ 只读消费 |
| 房间列表/信令 | ✅ 全局大厅 | ✅ 本节点大厅 |
| **对战数据中继** | ⚠️ 尽量不做 | ✅ **主要承担者** |
| 天梯/统计 | ✅ 仅认证节点上报 | 可选 |
| 自定义规则/插件 | ❌ | ✅ 自由 |

### 3.2 为什么必须联邦——这是成本问题,不是理念问题

对战中继流量是真实开销:一局 10 人对战 30–60 分钟,W3GS 包量不大但连接要全程保持。**在国内按流量计费的 CDN/带宽下,中继是唯一会随用户数线性烧钱的部分**,而地图分发靠缓存命中率可以摊薄。

所以:

- **首选 P2P**:UDP 打洞,大部分家宽能成功
- **次选自部署节点中继**:社区节点自己出带宽,权威服务器只做信令撮合
- **权威服务器兜底中继**:仅对打洞失败且无可用节点的情况,并设配额

这个切分让权威服务器的成本**几乎与在线人数无关**——它只做身份、索引、信令,全是小包低频请求。这跟 PvPGN 每个服务器都是孤岛、账号不互通的老模型正好相反:**账号互通,负载分散**。

### 3.3 游戏版本

国内主流仍是 1.24e / 1.26a(RPG 图、DotA),W3GS 协议和地图校验在 1.20 / 1.23 / 1.27 / 1.31 / Reforged 之间有差异。

好消息是 **war3parser 的 w3i version ladder(v8–v33)能直接推断地图要求的最低游戏版本**:`w3i.version` + `script_mode`(v28+ 才有 Lua)+ `graphics_mode`(v31+)。写进 manifest 后,客户端可以在进房间前就告诉玩家"这张图需要 1.31+,你当前 1.26"。又一个只有做了解析器才拿得到的能力。

## 4. 存储分层:国内 CDN + GitHub 冷备

按已确定的方向,三层职责:

```
真相源      GitHub 索引仓库(纯文本 JSON,可 diff/revert/重建)
   │
   ├─ 冷备   GHCR OCI artifact ── 异地、免费、灾难恢复
   │
   └─ 热路径 国内 OSS + CDN ──── 普通玩家实际下载的地方
```

**关键:国内 CDN 完全不需要被信任。** 客户端强制 digest 校验(见分发文档 §7.2),CDN 投毒会被直接拒绝。信任根是 GitHub 上那份 git 历史。这条性质带来三个实际好处:

- 可以用最便宜的国内 CDN,不用考虑其安全性
- 任何人都能搭镜像,不需要审核授权
- CDN 被墙/跑路/涨价,换一个 base URL 就行

### 4.1 成本结构提醒

国内 CDN 是**流量计费**(¥0.2–0.5/GB 量级),跟 R2 零出站费是完全不同的模型。地图分发是流量型负载,所以:

- 缓存命中率是第一指标。`/v1/blobs/<digest>` 的 `immutable` 语义(分发文档 §6.2)在这里价值更大
- 冷门图可以只放 GHCR/境外,国内 CDN 只缓存热门图,靠 probe 协议自动 fallback
- 联机中继流量**不要走 CDN**,走自部署节点(§3.2)

### 4.2 备案与责任

服务普通玩家 + 国内 CDN + 用户上传 = 需要面对备案主体的内容责任。建议:

- **国内节点做成只读镜像**,上传仍走境外主站的 Worker + PR 流程。国内节点角色是 CDN 而非信息服务提供者,风险显著降低
- 联机平台在国内的合规门槛更高(11 平台、网易对战平台都是有资质的公司在运营)。这不是技术能解决的,需要你自己判断做到什么规模、以什么形式

这一条我只陈述事实,怎么权衡是你的决定。

## 5. war3parser 需要新增的能力

按价值排序。**前两项同时服务地图站和联机平台,是真正的杠杆点**:

| # | 能力 | 服务于 | 难度 |
|---|---|---|---|
| 1 | `MapManifest`(见分发文档 §2.3) | 地图站 | 低 |
| 2 | **W3GS 校验值计算**(§1) | **两者** | 中,需核对 Aura 源码 |
| 3 | 最低游戏版本推断(§3.3) | 两者 | 低,纯逻辑 |
| 4 | slug/version 推断 | 地图站 | 低 |
| 5 | W3GS 协议编解码(新 crate) | 联机 | 高 |

2 和 3 现在就该做:它们是纯解析能力,不依赖任何后端决策,而且没有它们**第 3 块(连通)根本无从谈起**。

新增依赖很轻:`crc32fast` + `sha1`(或 `sha2` 已有生态),核心逻辑是按固定序列喂字节。

## 6. 建议的顺序

**不要三块并行。** 理由是它们的复杂度和风险差一个量级,而且有明确的依赖关系。

| 阶段 | 做什么 | 为什么是这个顺序 |
|---|---|---|
| **1** | `MapManifest` + W3GS 校验值 + 版本推断 | 纯本仓改动,零外部依赖,同时是后两块的地基 |
| **2** | 地图 registry(按分发文档路线) | 独立可用产品;此时已能做 `/v1/lookup` 反查 |
| **3** | 客户端从**地图管理器**起步 | `w3pkg install/sync`,先解决"下图"这个真实痛点 |
| **4** | LAN 伪造 + 隧道,接入现有平台 | 先做 GHost++/Aura 兼容的客户端,不自建服务器 |
| **5** | 自部署 lobby 服务器 | 有用户了再做 |
| **6** | 权威服务器 + 联邦身份 | 最后,因为它的价值依赖前面的用户量 |

**第 4 步的选择很重要**:先做一个能接入**已有** GHost++/Aura 服务器的客户端,而不是同时造服务端。这样你能在只写客户端的情况下拿到真实用户反馈,而且验证了最难的部分(LAN 伪造 + 协议兼容)。服务端可以晚半年。

### 最小可验证切片

阶段 1 做完后,你就能验证整个愿景里最不确定的那个假设:

```bash
war3parser-cli identity DotA_6.83d.w3x --game-version 1.26a
# map_size: 8123456
# map_info: 0x3a1f9c2d
# map_crc:  0x9f2c4a11
# map_sha1: 3f2a…
```

拿这个值去跟一个真实 GHost++ 房间广播的值对比。**对得上,三块连通就成立;对不上,后面全部要重新考虑。** 这个验证成本是几天,而不是几个月。
